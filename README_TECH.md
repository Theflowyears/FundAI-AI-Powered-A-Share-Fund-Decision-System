> 本文件是 **FundAI · AI-Powered A-Share Fund Decision System** 的技术主文档：
> 架构总览、每日决策流、算法口径（选基 / 仓位 / 风控）、十年实证与四窗口独立回测、
> 全程序审计与修复清单、已知边界与诚实结论。
> 项目定位与快速上手见项目首页 `README.md`（门面文档，本文件在发布快照里同名副本为
> `README_TECH.md`）；便携包说明见 [`README_PORTABLE.md`](README_PORTABLE.md)。

**它的证据**：仓库自带**十年（2017-09 → 2026-09）实证报告**与四窗口（牛/熊/震荡/全历史）
独立回测：固定基准仓位 + 十年消息面 + 反应型风控在 2017-09→2026-09 的**九个年度**上做到
**+85.8% / 最大回撤 19.9%**（同期沪深300 +18.6%）。所有结论都可用 `data/` 下的脚本逐条复现。

> **2026-10 更新**：默认策略已升级为「制度自适应组合 + 关基金级止损/止盈」，
> 并把基准/硬上限从 90%/95% 调整为 **80%/80%**；同一份最新数据
> （2017-09-28 → 2026-11-05）上全历史 **+187.0% / 最大回撤 21.4%**，
> 旧策略同口径是 +98.1% / 23.7%。上面的 +85.8% 是旧口径的历史记录，
> 数字不要混用。证据、取舍（牛市与近端行情会跑输）、回退方式见 **§25**。

> **关于账户参数**：起始资金、"目标线"与观察期都是**开箱默认值 + 可自定义参数**
> （网页参数面板或 `python app.py init --cash N`），它们只服务于界面进度显示与记账，
> **不是策略目标，也不构成任何收益承诺**。本系统是一个量化基金决策工具，
> 价值在**决策辅助、风控纪律与可复盘性**，不在于把某个金额变成某个金额。

**一句话架构**：多源新闻 + 十年电报库 + 涨停情绪 + 行情技术面 → 三路评分 + 事件语义 + LLM 研判
→ 评分驱动的**选基**与**固定基准仓位** → 反应型风控（止损/均线/冷却）→ 每日建议（人工执行记账）
→ 自动结算与自检命中率 → 网页可视化。

**先看这一条（诚实提示）**：日频方向预测的样本外上限通常在 55–60%，
本项目十年实测为 **52–56%**；**没有任何模型能稳定“预测”明天**。
所以本系统的定位是**决策辅助与纪律工具**，而不是“预测机器”。十年回测的结论是：
用**固定基准仓位（70%）+ 十年消息面 + 反应型风控（基金级止损 + 均线减仓 0.10 + 回撤冷却 0.10）**
在 2017-09→2026-09 的**九个年度、四个独立市场状态窗口**上做到 **+85.8% / 最大回撤 19.9%**
（同期沪深300 +18.6%），但**参数曲线并不平滑、单点最优不可信**（见 §6.5 与 §12）。
请把它当成研究/教学工具，不构成投资建议。

## 一、项目目标与硬约束

| 项 | 设定（默认值，均可配置） |
|---|---|
| 起始资金 | 由用户自定（`account.initial_cash`，`init --cash N` 写入账本）；**策略与金额无关** |
| 目标线 | 纯显示用的**可自定义进度基准**（`account.target_multiple` / `target_value`），**不参与交易决策、不代表收益目标** |
| 观察期 | 可自定义（`init` 时写入起止日期） |
| 标的 | 场外普通基金（股票型/指数型 C 类 + 债基），**不能直接买股票、不能加杠杆** |
| 执行 | 默认 `exec_mode=manual`：系统出建议 → 你在支付宝/天天基金操作 → 回填成交（账本与真实资金一致） |
| 交易约束 | T+1 确认、最短持有期（默认 7 天）内不可卖、赎回费随持有期递减、申购有最小金额 |
| 数据 | 免费/低配额通道（财联社、同花顺、东财、新浪、智兔/AKShare）；**无需任何密钥即可运行** |
| 运行环境 | Windows 10/11 + Python 3.9+；运行时**零第三方硬依赖**（numpy 可选，仅加速 10 倍） |

## 二、快速开始

**方式一：从发行包起步（推荐给新环境）** —— `dist/fundai-portable-<版本>.zip` 解压即用，
不含密钥/数据库/缓存，首次运行**自动生成 `config.json`**（内置通用起始基金池，
不加载任何人的 key 与本机地址）：

```bat
python app.py doctor          :: 环境自检
启动服务.bat                   :: 起网页（http://127.0.0.1:8787）并自动打开浏览器
python app.py run-daily       :: 收盘后跑一次研判
install_tasks.bat             :: （可选，管理员）按安装目录注册 6 个计划任务
```

**方式二：源码树（本仓库，含十年数据与研究脚本）**：

```bash
# 1) 依赖：仅标准库 + numpy（可选，用于 10 倍速向量化）
python -m pip install numpy

# 2) 初始化账户：金额由你自定（策略与金额无关）
python app.py init --cash 5000                  # 建账：起始资金 5000
python app.py init --cash 5000 --target 6000     # 可选：给界面画一条自定的进度基准线
python app.py init --cash 5000 --target-multiple 1.2   # 或用倍数表达同一条基准线
#   ↑ 目标线只影响界面"进度/还差多少"与回测里的达成标记，
#     不进入选基、仓位、风控的任何计算，也不是系统承诺的收益目标。

# 3) 每日流程（收盘后 ~21:30）
python app.py news-pull                 # 拉取多源消息 + 打标入库
python app.py run-daily                 # 研判 + 下单建议 + 快照 + 自检结算
python app.py signals-update --days 7   # 事件→次日涨跌样本结算（校准用）

# 4) 网页（默认 127.0.0.1:8787）
python app.py serve

# 5) 回测 / 研究（**已并行**，默认铺满 CPU；--jobs N 可限流）
python app.py backtest --months 6
python app.py event-model --days 4000 --select
python data/regime_study.py --dd 25      # 6000 组组合扫描（约 4 秒）
python data/regime_backtest.py           # 124 个引擎回测任务（约 4 分钟）
python tools/bench_parallel.py           # 并行加速基准（可复现的数字）
```

**打包 / 自检（各一条命令）**：

```bash
python tools/make_release.py     # 同步静态资源 + 生成 config.example.json + wheel/sdist/便携 ZIP
python tools/verify_release.py   # 从产物本身解压→起服务→跑测试（12 项检查）
python tools/audit_all.py        # 全量审计：24 个 CLI 子命令 + 30 个 Web 路由
```

**Windows 计划任务（已配置）**：`fundai_keepalive`（每 15 分钟保活）、
`fundai_intraday`（工作日 12:00 午间诊断）、`fundai_run_daily`（21:30 研判 + 补拍快照）、
`fundai_run_daily_late`（22:45 兜底）、`fundai_daily_signals`（20:30 事件样本结算）、
`fundai_direction_check`（23:05 **AI 次日方向判断的自检**：补记方向 + 结算命中率，
独立于研判任务，研判当天已跑过也会照常补齐）。
新环境用 `install_tasks.bat`（管理员）按安装目录重新注册。

> **AI 次日方向判断（自动记录 · 自检命中率）怎么跑**（2026-09-12 修复）：
> 方向 = 合成评分（平滑后）经 `analysis.view_of` 推导，判断日收盘给出、写一行到
> `screening.db` 的 `direction` 表；下一交易日收盘后用当日涨跌结算命中
> （看多=涨、看空=跌、中性=|涨跌|≤0.3%），命中率在「消息与进化」页。
> 修复前这一步嵌在 `run_daily` 中段，遇到 `has_record(D)` 短路（当天已跑过一次、
> 晚间只补拍快照、或白天先手动跑）就整体跳过；周末/节假日又因面板判定条件过窄而
> 空白。现在：`run_daily` 主流程与短路路径都会跑 `Engine.direction_record()`，
> 也可单跑 `python app.py direction-check [--date D]` 补记/结算，写库失败不再静默。

## 三、架构总览

```
数据层        clsdb(SQLite 电报库) · datasource(行情/净值/多源K线) · microstructure(涨停情绪)
              screening(SQLite 消息库/打标/学习词/方向记录/午间记录) · calib(结算样本)
              api_usage(分源配额计数/降级状态，持久化到磁盘)
算法层        lexicon(词典/符号折算) · semantics(事件语义) · news(消息聚合/口径/按日历史聚合)
              analysis(量化分+LLM+动态权重) · indicators(技术指标) · strategy(选基/仓位/风控/轮动)
              microstructure(情绪分/题材热度) · event_model(事件→方向 样本外模型)
              risk_overlay(预测型风控，默认关闭) · intraday(午间诊断)
调度层        engine(run_daily/simulate/backtest/state_payload) · web(HTTP API + 静态页) · llm_news(LLM 逐条定级)
配置层        settings(默认值+校验+热重载) · param_docs(126 个参数的中文说明元数据) · configedit(校验后写入+备份+回滚)
呈现层        web/static/{index.html,app.js,style.css,vendor/echarts.min.js} · app.py(23 个 CLI 命令)
保障层        tests/(260 项) · data/namecheck.py(未定义名扫描) · 一致性校验(资金守恒)
研究层        data/harness.py(评估内核/窗口枚举) · regime_study.py · regime_backtest.py(阉割+最终组合)
```

### 每日决策流（`run_daily`）

```
index_history → D(最近收盘日) → 结算到期 T+1 订单 → 午间诊断结算
 → 量化分(analysis.score_market)  +  消息分(重点事件口径 / 人工打标优先)  +  情绪分(涨停微观)
 → 动态权重微调(消息±3% / 情绪±3%)  →  合成评分(量化50% 消息35% 情绪15% 基准)
 → 题材热度(3日衰减)  →  选基(动量+多因子, 同主题≤1)  →  仓位(固定70%基准 → 硬上限80%)
 → 反应型风控(跌破MA60/120减仓, 底仓40%; 单只-8%止损; 峰值回撤10%冷却5天)
 → 订单(买入/赎回/转换)  →  记录(calc 评分明细)  →  快照  →  资产曲线自愈回填
```

## 五、算法体系

### 5.1 三路评分（合成比例见下）

| 维度 | 来源 | 权重（基准） | 十年实测边际 |
|---|---|---|---|
| 量化技术面 | MA20/60/200、RSI、5/20 日动量、乖离、量价 | 50% | 主要信号来源（含短期反转） |
| 消息面 | 财联社/东财/新浪 → 事件语义 + 词典 + LLM 定级；人工打标优先 | 35% | 事件级 +3~+5pp，**日级 IC 仅 +0.02** |
| 情绪微观 | 涨停池/炸板率/晋级率/涨跌停结构（借鉴 Cailianpress-Feishu-Bot） | 15% → **现 10%** | IC −0.077（轻微反向） |

**动态权重**：消息净情绪 |net|≥4 → 消息 +3%；情绪分位两端 → 情绪 −3%；波动率 ≥90% 分位 → 两者各 −3%；
限幅 消息∈[0.25,0.40]、情绪∈[0.05,0.15]（`analysis.dynamic_weights`，每日在研判文案中列出）。

### 5.2 消息面口径治理（三轮迭代）

1. **事件语义层**优先（央行/政策/业绩/增减持/地缘/权益披露…），词典作兜底；
2. **例行噪音自动归档**：ETF 溢价、机构持股披露、同模板刷屏（骨架相似度 ≥0.82 自动归并）；
3. **词典层关闭**（`news_dict_mode="off"`）+ **重点事件口径**（`news_focus_events`）+ 反向刻度换算；
4. **LLM 逐条定级**（`news_llm_enable`，默认每天 ≤120 条，判中性/无关即**一票否决**，
   与词典标签一致率 94%，但**不提高日级命中率**——定位是降噪与人审提示，方向默认不加权）。

### 5.3 事件语义层实测（十年，2189 交易日）

| 事件×方向 | 样本 | 命中率 | 增量（相对基线） | p |
|---|---|---|---|---|
| 股东增减持·利多 | 27,988 | 56.0% | **+5.5%** | <0.001 |
| 业绩·利多 | 13,290 | 54.8% | **+4.3%** | <0.001 |
| 词典兜底·利多 | 198,845 | 54.0% | **+3.5%** | <0.001 |
| 产业政策·利多 | 8,810 | 53.5% | +3.0% | <0.001 |
| 央行宽松·利多 | 7,522 | 53.4% | +2.9% | <0.001 |
| 地缘冲突·利空 | 17,365 | 49.1% | −0.4% | 0.31 |
| 词典兜底·利空 | 73,745 | 45.4% | −4.0% | <0.001 |

> ⚠️ 5.4 年窗口曾得出"词典层两个方向都是负增量"的结论，十年样本推翻之（窗口偏差）。
> 但**日级口径对照**显示：词典全量 / 仅重要 / 关闭三者的 IC（+0.016~0.021）与命中率
> （49.1~49.7% vs 基线 50.5%）**差异都在噪声内** → 口径保持"重点事件 + 词典关"（更简单、可解释）。

### 5.4 题材热度（涨停概念 + 风口 → 选基主题）

单日强度 = 概念涨停家数 + **0.5×**最强风口家数（去重）→ 转**当日占比** → 按 [0.5/0.3/0.2]
时间衰减（新→旧）→ **持续性加成**（窗口内每多 1 天 ×1.12）→ 归一化；
今日占比 ≥ 其余日均值 1.5 倍且 ≥8% → 标 **🔥 点火（新热点）**。算法与传参顺序无关。

### 5.5 事件→方向模型（样本外，仅作参考信号）

walk-forward（预测第 t 日只用 <t 数据）+ 选择性出手（阈值只在训练窗内定）+ 特征子集对照
+ 选择期/留出期分离。特征：事件三组×多空、制度状态（均线/波动分位/回撤）、跨市场风格强弱、
制度交互项（趋势×位置、趋势×连涨跌、波动×连涨跌…）。

**十年结果（2190 交易日 / 样本外 2130）**：方向命中 **52.3% vs 基线 50.3%（+2.0pp）**，
选择性出手 51.4–54.3%，留出期 +1.4pp；**策略跑输买入持有（0.9659 vs 1.1138）**。

### 5.6 风控：从"预测型"转为"反应型"

| 规则 | 参数 | 说明 |
|---|---|---|
| 单只浮亏 **−8%** → 止损清仓 | `risk.fund_stop_loss_pct` | 反应型，规则明确 |
| 单只浮盈 +10% 锁一半 / +25% 全落袋 | `fund_take_profit_pct/_full_pct` | 止盈纪律 |
| **跌破 MA60/MA120 → 每档减 20%**（底仓 40%，MA20 破位噪声大默认跳过） | `ma_break_step/_max/_floor/_skip_ma20` | 新增，站回均线自动恢复 |
| 峰值回撤 **10% → 冷却 5 个交易日**（降仓至 25%） | `peak_trailing_pct`、`rearm_days=5` | 组合级 |
| 组合止损 −15% | `portfolio_stop_pct` | 组合级 |
| 硬上限 **80%**（永不满仓） | `equity_hard_cap` | 全局 |
| 预测型过滤（模型 P(涨)） | `risk_overlay_enable=false` | **默认关闭**（十年负贡献） |

### 5.7 仓位结构（三层，最终定稿）

> **2026-10 更新**：最终默认已改为「制度自适应组合 + 基准 80%/硬上限 80% +
> 关基金级止损/止盈」，见 §25；本节保留 2026-09 的定稿记录，数字不要与 §25 混用。

```
最终权益目标 = clamp( 固定基准 70% + 调整带(默认关闭) − 反应型减仓 − 风控降档 , 0, 80% )
              基准：equity_base_mode="fixed"、equity_base_fixed=0.70（硬上限 0.80，永不满仓）
              调整带：±position_band_max（默认 0；制度+情绪驱动，不用账户收益）
              反应型减仓：**默认开启** ma_break_step=0.10（跌破 MA60/MA120 各减 10%，合计≤40%，底仓 40%）
              风控降档：组合级触发（自峰值回撤 ≥15% 或 相对本金亏 ≥15% 且评分<25）
                        → 权益降至 25%，冷却 5 个交易日后自动解除；
                        带**迟滞**：回撤收敛到阈值 −5pp 才重新武装（否则会永久锁死，见 §十四 第 1 条）
```

> 2026-09-11 更新：指数级择时层从"默认关闭"改为**默认开启**。上一轮"关闭"的结论来自

### 6.1 权重维度第二轮试错（5760 个组合，追求高收益 + 回撤不失控）

第一轮固定了权重，第二轮把**内部算法权重**也纳入扫描（消息 ∈ {20%,30%,35%,45%}、
情绪 ∈ {0%,10%,20%}、量化拿剩余）、基准仓位 ∈ {60%,70%,80%,90%,100%}、
基础模式 fixed/score、调整带开/关、风控层 4 种、硬上限 ∈ {80%,90%,100%}，
**全网格在两期都算**（选择期 1158 天 / 留出期 772 天，含 20bp 摩擦）。

**收益/回撤前沿（三个代表点）**：

| 档位 | 组合 | 选择期 | 留出期 |
|---|---|---|---|
| 最高收益 | 消息20%/情绪20% **score基准100%** 无风控 上限100%（≈满仓） | +10.8% / 38.4% | **+17.5% / 20.1%** |
| **★ 采纳（高收益+回撤可接受）** | 消息20%/情绪0–10% **fixed基准70%** 上限80% **不叠加指数级择时** | +10.8% / 29.3% | **+13.0% / 15.4%** |
| 两期最稳 | 消息20%/情绪0% score基准60% 均线+冷却（降仓25%）上限80% | +12.5% / 18.2% | +7.8% / 9.6% |

筛选口径：选择期回撤 ≤30%、留出期回撤 ≤20%、两期收益 >0（5760 组中 3672 组满足）；
"采纳"取其中留出期收益最高者，"两期最稳"取 min(两期 收益/回撤) 最大者。

**指数级风控层的定向代价**（基准 70%/消息 20%/情绪 10%）：

| 风控层 | 选择期 | 留出期 |
|---|---|---|
| **无（采纳）** | +10.8% / 29.3% | **+13.0% / 15.4%** |
| 仅回撤冷却（降仓25%） | +21.5% / 18.7% | **−3.9% / 12.8%**（追跌杀跌） |
| 仅回撤冷却（降仓50%） | +14.1% / 25.6% | +8.1% / 14.5% |
| 仅均线减仓 | +2.6% / 23.5% | +7.4% / 10.1% |
| 均线+冷却（降仓25%） | −3.2% / 18.0% | −7.8% / 12.9% |
| 均线+冷却（降仓50%） | +0.8% / 22.6% | +7.4% / 10.1%（冷却上限高于均线减仓后的 40% 下限，不再起作用） |

**结论**：
1. **指数级择时层（均线减仓 / 回撤冷却）在留出期让出的收益多于减少的回撤** → 默认关闭
   （`risk.ma_break_step=0`、`peak_trailing_pct=1.0`），需要"低回撤档"时改回 `0.2 / 0.10` 即可；
2. **基金级风控全部保留**（此处为指数级模拟，未建模基金级规则）：
   单只 −8% 止损、+10%/+25% 止盈、组合止损 −15%；
3. **消息权重降到 20%**（量化 70%）在留出期更好——与"消息面日级 IC 仅 +0.02"一致；
4. 采纳组合留出期 **+13.0% / 回撤 15.4%**，选择期 +10.8% / 29.3%，两期都为正；
   情绪分历史只有 266 天（快照回填所限），故 0% 与 10% 档在两期等价，线上仍保留 10%。
5. 定向对照中的所有风控层都用**显式设计值**（均线步长 0.2、合计上限 0.4、冷却阈值 10%、冷却 5 天），
   不继承线上开关，避免"线上关掉某层 → 对照表随之变化"的复现漂移。

> 复现：`python data/weight_combo_study.py`（5760 组合全网格，结果存 `data/weight_combo_study.json`）。

指数级 harness 只把消息/情绪分用于"评分驱动仓位"，测不出"消息面影响**选基**"。
所以子系统阉割对比改在**真实引擎**（`Engine.backtest`：point-in-time 重建备选池、真实申赎费、
基金级止损止盈、最短持有）上做，回放已接入十年消息库的当日消息分。

|---|---|---|---|---|

**四条结论**：
1. **消息面是全系统最大的收益来源**：关掉它，全历史 **+65.0% → +25.5%**（少 40pp），
   且回撤反而更大（24.0% → 28.6%）。`news_weight` 取 0.20 还是 0.35 几乎无差别——
   **关键是"有没有消息面"，而不是给多少权重**；
2. **指数级择时层在基金级真有价值**（与上一轮指数级结论相反）：`均线减仓 + 回撤冷却`
   把全历史 **+65.0% → +80.1%**、回撤 **24.0% → 17.3%**、熊市 **−11.6% → −5.8%**；
   代价是牛市/震荡弹性变小（+14.5%→+7.5%、+13.0%→+4.9%）；
3. **基准 80% 与"关动态权重"都能提高收益但越界**（回撤 31.1% / 28.1% > 25% 上限），
   在 25% 上限内**不可采纳**；
4. **三处"改了没反应"是回放不覆盖，不是"没用"**：① 调整带 ±10% 小于 `regime_step`
   调仓阈值（12%），被阈值吸收；② 题材热度因子在历史区间没有热度快照（`heat_map` 为空）；
   ③ 预测型过滤器的信号文件只有"当天"的 p_up，回放没有历史信号序列。
   它们各自的十年结论来自专门脚本（`reactive_study.py`、`micro_study.py`、
   `risk_overlay_eval.json`），**不能**用本表一句"无影响"代替。

| MA 步长 0.15 + 冷却 0.10 | +88.54% / 18.1% | +5.25% | −12.22% | +12.53% |
| MA 步长 0.20 + 冷却 0.10 | +80.09% / 17.3% | +7.46% | **−5.84%** | +4.87% |
| MA 步长 0.30 + 冷却 0.10 | +32.09% / 18.5% | +4.31% | −4.30% | +7.51% |
| 关闭 MA 减仓（只留冷却 0.10） | +50.71% / 25.5% | +14.63% | −9.25% | +20.61% |
| MA 0.10 + 冷却阈值 0.08 | +22.89% / 19.4% | +0.32% | −6.90% | +24.39% |
| MA 0.10 + 冷却阈值 0.15 | +87.58% / 18.3% | +15.86% | −11.10% | +9.88% |

> **必须看这段**：步长从 0.05 → 0.10 → 0.15 → 0.20 → 0.30，全历史收益是
> **+55.8% → +85.8% → +88.5% → +80.1% → +32.1%**：相邻档位能差 30–50pp，
> 冷却阈值 0.08 与 0.10 之间更是 +22.9% vs +85.8%。**这不是"精细调参的空间"，
> 而是"单路径回测的方差"**——每个参数值只对应一条历史路径，路径依赖（轮动时点、
> 止损触发次序）会把结论放大成噪声。因此：
> 1. 只应把 **0.10–0.20 视作一个"可接受平台"**（全历史 80–88%、回撤 17–20%、
>    四窗口均不越界），不要相信其中某一个是"最优"；
> 2. 平台之外（0.05 / 0.30）明确变差，可以排除；
> 3. 想更稳就选 **D（关动态权重，回撤 13.5%）** 或 **F（熊市 −3.4%）**，
>    它们用 10–15pp 的全历史收益换取更低的波动与更好的防御——
>    这三档都在参数面板里**一键可切**（`risk.ma_break_step` / `peak_trailing_pct` /
>    `dynamic_weights` / `news_weight`）。

> 复现：`python data/regime_backtest.py`（全部变体）或 `--only final_H,sens_ma015,…`（选跑），
> 结果存 `data/regime_backtest.json`。

## 十二、已知边界与诚实结论

1. **不承诺高命中率**：日频方向是接近有效市场，长期 52–56% 已是实测上限；
2. **不承诺任何收益**：本系统是**量化基金决策工具，没有"收益目标"这个概念**——配置与界面里的
   "目标线/进度"只是用户自定的显示基准，不参与选基、仓位与风控的任何计算，也不再进入 LLM 提示词。
   文中出现的 +85.8%、+187.0% 等都是**历史回放的区间结果**（一律同时给出同期沪深300 基准与最大回撤），
   说明的是"这段历史上怎么走"，不是"未来会怎样"；系统提供的是纪律、口径与可复现的工具体系；
3. **参数曲线不平滑，单点最优不可信**：同一套逻辑只改均线减仓步长
   （0.05/0.10/0.15/0.20/0.30），全历史收益是 +55.8/+85.8/+88.5/+80.1/+32.1%——
   相邻档位差 30–50pp。这**不是可精细调参的空间，而是单路径回测的方差**；
   只能把 0.10–0.20 当"可接受平台"，并把平台外的档位排除（详见 §6.5）；
4. **回放口径有覆盖盲区**（会让人误以为"改了没用"）：调整带 ±10% 小于调仓阈值 12%
   被吸收；题材热度因子在历史区间没有热度快照；预测型过滤器没有历史信号序列。
   这三者的结论只能来自各自的专门脚本，**不能**用"回放里逐位相同"当作"无效"；
5. **指数级 ≠ 基金级，且两者会给出相反结论**：同一组"均线减仓 + 回撤冷却"，
   指数级近似说"让出收益更多"（§6.3），基金级真实引擎说"同时提高收益、压低回撤"（§6.4）。
   原因是基金级多了债基底仓、基金级止损与轮动路径，**结论以基金级为准**；
6. **样本外会失效**：上一轮"选择期冠军"（组合⑩）在留出期转负，是常态而非意外；
7. **数据依赖**：财联社 10 年电报、同花顺情绪、行情通道都可能变更或限流；
   K线缓存曾被兜底通道的短区间覆盖过一次（见 §十四 第 8 条），现在写回取并集、读取合并双键；
8. **本仓库全部结论可复现**（脚本在 `data/`，报告在 `data/*.json`），但**不构成投资建议**。

## 十六、账户参数可配置 + 全链路并行加速

### 16.1 起始资金与"目标线"：都只是账户参数，与策略无关

系统**不设收益目标**。下列参数只服务于记账与界面显示：

| 参数 | 作用 | 明确不影响 |
|---|---|---|
| `account.initial_cash` | 建账时写入账本的起始现金；组合止损与收益率的计算基准 | 选基、仓位、风控规则 |
| `account.target_multiple` / `target_value` | 界面"目标线 / 进度 / 还差多少"与回测达成标记的**显示基准** | 任何交易决策；也不再进入 LLM 提示词 |
| `account.start_date` / `end_date` | 观察期起止（界面与报告用） | 策略算法 |

入口：`python app.py init --cash <金额>` 建账（可选 `--target` / `--target-multiple` 指定显示基准），
或网页参数面板「运行与服务」组，保存即生效（自动备份、可回滚）。

规则细节（`tests/test_account_plan.py` 覆盖）：
* **本金来自账本**（记录实际投入多少钱，改配置不会篡改历史）；
* 显示基准每次运行按「账本本金 × 倍数」重算，改倍数立即生效、不需要重新 `init`；
* 旧配置若只有 `target_value` 而没有 `target_multiple`，按 `target_value` 走（升级不漂移）；
* 倍数 ≤ 0 视为非法（`settings.validate` 拒绝），配置写坏会明确报错而不是静默 0；
* **2026-11 口径变更**：LLM 提示词与数据包里**不再出现本金/目标/倍数**——旧版会写
  "受托用 X 元半年做到 Y 元（+Z%）"，那会诱导模型为凑数字给建议。回归锁见
  `tests/test_account_plan.py::LlmPromptTest`。

### 16.2 并行加速（24 物理核 / 32 线程实测数字）

新增 `data/parallel.py` 作为并行底座，并明确了两条纪律：**只并行纯计算**（会写共享文件的
步骤留在主进程串行）、**只并行值得并行的部分**（过轻的任务并行反而更慢）。

| 任务 | 改造前（串行） | 改造后（并行） | 加速 |
|---|---|---|---|
| `data/regime_study.py`（6000 组组合 × 4 窗口） | 约 60–90 秒 | **3.9 秒** | ~20× |
| `data/regime_backtest.py`（31 变体 × 4 段 = 124 个引擎回测） | 实测累计 **6155 秒** | **243.6 秒** | **25×** |
| `data/audit.py`（23 个 CLI 子命令） | 约 2–3 分钟 | **34.9 秒** | ~4× |
| `data/audit_web.py`（34 个路由） | 约 90 秒 | **16.8 秒** | ~5× |
| `harness.build_base`（2172 天逐日指标） | 1.9 秒 | 0.9 秒 | 2.2× |
| 评分序列（15 组） | 0.08 秒 | **不并行**（并行实测 0.7 秒，更慢） | — |

实现要点：进程池（CPU 密集）× 线程池（HTTP/子进程）分工；worker 用 initializer 加载共享数据、
**自己读磁盘缓存**（不把几 MB 对象 pickle 给每个任务）；`FUNDAI_JOBS` 环境变量或 `--jobs N` 可限流；
研究跑批把计数器重定向到 `data/cache/study_usage.json`，避免并行 worker 争抢线上配额计数文件。

**命令行日常命令也接上了并行**（2026-09-12）：

| 命令 | 并行方式 | 说明 |
|---|---|---|
| `news-score-db [--jobs N]` | 进程池（纯计算） | 几十万条电报的正则+词典+事件语义打分；**读任务与写库留在主进程**（SQLite 单写者），worker 各自加载一次词典，结果与串行逐字段一致 |
| `news-fetch-db [--jobs N]` | 线程池（纯 I/O） | 把回溯区间均分成 N 段、每段一个线程各走时间游标翻页；写库靠 WAL 并发提交，`id` 主键 + INSERT OR IGNORE 幂等，重复抓取不重复计条 |

## 十八、发布快照的缓存整合（`data/cache/` → `data/cache.db`）

**问题**：`data/cache/` 是按日/按代码切分的缓存——`micro_<date>.json`（约 260 个交易日）、
`nav_<code>.json`（几十只基金）、`kline_*.json`（指数长历史）……单个体积只有几 KB，
但**文件数到几百上千**。上传到 GitHub / 云盘 / 聊天工具时，瓶颈在"文件数"而不是"数据量"：
逐个文件的开销、漏传风险、增量同步成本都远超内容本身。

**做法**：发布快照把它们收进**单个 `data/cache.db`**（SQLite），键=原文件名，值=紧凑 JSON
（≥2KB 且压缩收益 ≥10% 时用 LZMA，实测 321/337 条命中）：

| | 目录式 JSON | `data/cache.db` |
|---|---|---|
| 文件数 | 337 | **1** |
| 占用 | 4.86 MB | **1.06 MB** |
| 发布目录总文件数 | 458 | **121** |

**运行时**（`fundai/cachestore.py` + `util.load_json()` 的只读回退）：

* **磁盘 JSON 优先、库里快照兜底** —— 本机跑出来的缓存永远比仓库里的快照新，
  所以加这层**不改变本机任何行为**（本机 260 项测试结果与加之前逐项一致）；
* 缓存路径被**重定向到别处**时（离线回测/审计用例会把 K线缓存指到临时目录），
  自动让路、不回退查库——保证"文件系统说了算"的语义，否则那些用例的
  "缓存为空"前提就不成立了（这条是实测踩出来的：删掉 JSON 后有两个离线用例变红，
  加了这个判断才恢复）；
* 值为 LZMA 时按魔数自动解压；坏值/缺键一律返回调用方给的默认值，绝不抛；
* 写入路径（`util.save_json`）不变，本机继续写 JSON 文件；
  环境变量 `FUNDAI_CACHE_DB=0` 可整体关闭这层。

**工具**：`python tools/cache_to_db.py [--keep-files|--dry-run] [目录]`
（`--keep-files` 只打包不删，用于先对比体积）。

**回归证据**：删掉全部 337 个 JSON、只留 `cache.db` 后，
· 指数长历史 2433 根、校准收盘序列 2433 天、情绪快照与净值代码数与删前**逐位一致**；
· 全量测试与本机失败清单对比：**新增回归 0 项**（两个因"缓存为空"前提被破坏的离线用例已按上文修好）。

## 二十、"首页打不开、卡在大盘指数加载中"事故复盘（2026-09-15）

### 20.1 现象与真相

**现象**：打开主界面一直转圈，永远停在"大盘指数加载中…"；但**后端接口全部正常**
（`curl /api/state` `/api/indices` 都是 200，毫秒级返回）。所以既不是死锁，也不是性能问题。

**真相**：`fundai/static/app.js` **有一处语法错误**：

```js
const _btnMkt = \;          // ← 整份文件解析失败
```

起因是我用 shell here-string 打补丁时，`$("btnMktRefresh")` 里的 `$` 被 shell 吃掉、
连同转义反斜杠一起写进了文件。浏览器遇到脚本语法错误会**整份放弃执行** →
`loadAll()` / `renderIndices()` 一个都不跑 → 页面永远停在初始的"加载中"占位文本。
**后端测试、接口测试、单元测试全都测不出这种故障**，因为服务端没有任何异常。

> 教训：**静态资源必须有语法级检查**。现在 `tests/test_frontend_static.py` 用
> `node --check` 逐个校验静态 JS，并扫描 shell 转义残留（`= \;`、`\$(`、行尾孤立 `\`）、
> 校验 `index.html` 引用的资源存在、以及两处静态布局逐字节一致。缺 node 时相关用例
> 带原因跳过，其余检查照跑。

### 20.2 第二个坑：常驻服务永远跑旧代码

前端是**实时读盘**提供的（改完刷新页面就是新版），但 Python 后端是**常驻进程**——
而 `fundai_start_hidden.py` 的逻辑是"端口被占用就静默退出"。于是：

* 前端已经更新 → 开始请求 `/api/market/overview`、`/api/market/intraday`；
* 后端还是几小时前的进程 → 这两个接口 **404**；
* 界面上就表现为"新组件一直转圈 / 看着像卡死"。

修法（两层）：

1. **代码指纹**：`fundai/web.py::code_stamp()` 用源码 (相对路径, mtime, size) 算指纹，
   服务启动时记录、通过 `GET /api/version` 暴露。**只统计源码**——
   第一版把 `__pycache__/*.pyc` 也算进去了，于是每次启动指纹都变、服务自己把自己
   判成旧版反复重启（当天踩到并修掉，注释保留在函数里）。
2. **自动换新**：`fundai_start_hidden.py` 保活时比对指纹：
   * 一致 → 静默退出（原行为）；
   * 不一致 → **优先请求旧服务的 `POST /api/restart`**（旧服务先回 200，再后台拉起
     `--relaunch` 新进程、等端口释放后自己 `os._exit(0)`）——不需要 taskkill 权限；
   * 老版本没有该接口 → 退回"停进程再启动"，且**只有确认监听者是 python 进程才动手**；
     读不到进程名时宁可只记日志、绝不误杀。

### 20.3 排查这类问题的正确姿势

| 顺序 | 动作 | 本次结果 |
|---|---|---|
| 1 | 后端接口逐个打（含超时） | 全部 200、毫秒级 → 排除后端/死锁/性能 |
| 2 | 确认"在跑的服务是哪个版本" | 启动时间 12:51 vs 我改代码 13:4x → 后端是旧代码 |
| 3 | 看服务实际吐出的静态文件 | 是**新版** app.js（实时读盘） |
| 4 | **静态 JS 语法检查**（`node --check`） | ★ 命中：`src/app.js:1455 SyntaxError` |
| 5 | 修 + 加回归测试（语法 + 转义残留 + 资源引用） | 5 项新测试全绿 |

关键点：**"接口都好但页面不动"几乎总是前端问题**；反过来"页面不动且接口挂"才是后端问题。
这次先看接口就省掉了在死锁上白找的时间。

## 二十一、四个操作性修复 + 配额口径更正（2026-09-15 第二轮）

这一轮的四个问题都不是"算法不work"，而是**功能存在但用不上 / 语义被误解**。
逐条记录现象、根因与验收方式——因为其中两条的根因是**"我以为是那样，其实不是"**。

### 21.1 午间复盘：从来没有自动跑过，也没法手动启动

**现象**：午间复盘（上午收盘后给下午观点）在界面上**完全看不到**，计划任务里也没有它，
只能靠人记得敲命令。

**根因**（三层，缺一层都跑不起来）：

1. **`intraday.run_midday` 没有对外入口**——它是 `run_daily` 内部调用的一个函数，
   没有 CLI 命令、没有 HTTP 接口，所以既不能定时也不能手动；
2. **没有注册计划任务**：`install_tasks.bat` 只注册了收盘后的任务链，11:35 这个时点没人叫它；
3. **界面没有组件**：大盘概览卡有，午间观点卡没有，用户自然以为"这功能不存在"。

**修法**：

| 层 | 改动 |
|---|---|
| 语义 | `fundai/intraday.py` 新增 `status(days=14)`：返回时段、今日诊断、观点文本、历史命中统计与"为什么没跑"的提示 |
| 接口 | `GET /api/intraday`（状态）、`POST /api/intraday/run`（立刻跑一次）、`POST /api/intraday/settle`（收盘结算命中） |
| CLI | `python app.py intraday-pulse`（含 `--date`、`--settle`）与 `python app.py intraday-status` |
| 任务 | `install_tasks.bat` 扩到 **7 个任务**：新增 11:35 `fundai_intraday` 与 15:05 `fundai_intraday_settle` |
| 界面 | 主界面新增**午间复盘卡**（在大盘概览之上）：时段徽标 + 今日观点 + 自检命中率 + **「立刻复盘」/「结算」两个按钮** |

**验收**：`POST /api/intraday/run` → `ok=true`、观点"震荡（下午大概率维持震荡）"；
`POST /api/intraday/settle` → `已结算：命中（下午 -0.0）`；`intraday-status` 显示 `2/2（100%）`。

> 设计取舍：午间复盘**只允许当天**补跑（`run_midday` 拒绝非当日日期）——
> 拿今天的行情去"复述"昨天的上午没有意义，且会污染自检命中率。

### 21.2 成交记录只有基金代码，没有名称

**现象**：成交/委托表里一行行全是 `004643`、`008327` 这种代码，要自己去搜。

**根因**：名称解析函数 `name_anywhere(code)` 早就存在，但**只被持仓解析用**；
成交记录接口直接回吐账本里的原始行。而账本表里**只存代码**（这是对的，代码是主键）。

**修法**：

* `GET /api/orders` 逐条补 `fund_name`；
* `engine.state_payload()` 额外产出**代码→名称映射**，覆盖
  `当前动态池 ∪ config 池 ∪ 全量候选池 ∪ 全部持仓 ∪ 账本里出现过的所有代码 ∪ nav 缓存`，
  供持仓、待执行、成交三张表共用；
* 前端表格改为 **名称 + 代码** 双列（名称在前，代码小字）。

**验收**：6 条订单全部有名称（`004643 → 南方中证房地产ETF发起联接C`），
映射表 54 条、**账本里的代码 0 条未命中**。

> 修的过程中踩到一个自己造的坑：计算映射的那段被插到了使用它的 `pool_info` **之后**，
> `fund_names` 引用未赋值变量 → `/api/state` 直接 `UnboundLocalError`（页面会全白）。
> `tests/test_fix4_ops.py` 与 `tools/audit_all.py` 都没覆盖"state 能出得来"这条，
> 是**端到端冒烟脚本**先抓到的——所以现在打包流程里保留了这个冒烟步骤。

### 21.3 新闻词典：慢、且学错了东西

**现象**：主动标注消息时页面卡住好几秒；而且学出来的"词"里有一堆 `的、了、和` 之类的碎片。

**根因**（两条，都是真错）：

1. **学的东西错了**：旧 `learn_all()` 在句子上开**滑动窗口枚举 n-gram**，
   再按词频挑候选——所以"规划"和"规"、"划"这种碎片同台竞争，
   还会把 `央行行长` 切成 `央行行`/`行行长`。它学的是**字面共现**，不是**语义关联**；
2. **时机错了**：`rate_item()` 里**同步**调 `learn_all()`，标注一条就要全量重算一遍，
   消息一多就是 O(n·ngram) 的卡顿。

**修法**（按用户明确要求：**不要抓关键词，只学内在联系**）：

* **词典来源固定**：可学词表 = `lexicon.FIN_TERMS`（约 400 个金融术语），
  **不再从语料里凭空生成词**。这直接消灭了碎片词与切词错误；
* **扫描器换成 Aho-Corasick 自动机**（`lexicon._build_automaton` / `scan_terms`）：
  一次扫描、最长匹配、不重叠，只认词表里的**完整术语**；
* **学的对象变成"术语 × 方向"的关联强度**：对每个术语统计它在
  "次日涨 / 次日跌"两组消息里的文档数，用**提升度（lift）**衡量关联，
  并设 `MIN_DOCS=2`、`MIN_TERM_DOCS=2`、`RELEVANCE_MIN=1.35`、`MAX_TERMS=400`
  与子串剪枝（`新能源汽车` 命中时不再重复计 `汽车`）；
* **标注改为异步**：`ScreeningStore.learn_async()` 后台重算（300ms 去抖），
  `rate_item()` 立刻返回；需要确定结果时用 `wait_learn()`。

**验收**：2000 条消息的扫描 < 1 秒（旧实现按 n-gram 枚举要十几秒）；
学出的词全是完整术语（`['规划','证券','新能源汽车','实施','人工智能','交易所','落地','国债','A股','整车','涨停','自动驾驶']`），
**非白名单词 0 个**。

> 一句话总结这次纠正：**词典不是"从新闻里猜词"，而是"用已知金融词汇去量新闻与行情的内在联系"。**

### 21.4 仓位：能不能全仓？独立的 200 元流动池

**问题**：既然目标是**提高资金使用效率**（而不是"留一堆现金图安心"），那**不全仓是不是不合适**？
用户说明有**项目外**的额外资金，必要时可以补进 200 元做流动池。

**先纠正一个被误读的语义**：原来的"20% 现金"不是"永远空仓 20%"，
而是**基准仓位 0.9 × 硬上限**共同压出来的结果。

**修法**：新增参数 `strategy.liquidity_reserve_yuan`（元，绝对金额，不是比例）：

* 语义 = **至少**保留这么多现金；**不是**强制保留更多，比它多出来的现金照常可以投出去；
* 实现 = `cap_from_reserve = max(0, (total - reserve) / total)`，
  取它与 `equity_hard_cap` 的较小值作为硬上限；
* 本金变大时同一笔储备的占比自然下降，上限自动放松
  （储备占到账户 20% → 上限被压到 80%；账户越大，同一笔 200 元越不占比重，
  上限越贴近 `equity_hard_cap` 本身）。

**当时的取值（2026-09-15）**：`equity_base_fixed=0.90`、`equity_hard_cap=0.95`、
`liquidity_reserve_yuan=200`、`position_band_max=0`（调整带关闭）。

**已知代价（诚实说明）**：十年回测里 **80% 上限的最大回撤是 31%、95% 上限更高**。
用户当时明确选择"资金使用效率优先、接受更大回撤"，所以按 0.95 交付。

> **2026-11 已更正（见 §25）**：用制度自适应组合 + 关闭基金级止损/止盈重跑后，
> 定稿档位改为 **`equity_base_fixed=0.80` / `equity_hard_cap=0.80`**（`liquidity_reserve_yuan` 仍为 200）。
> 同一份最新数据上 80/80 全历史 +187.0%/DD21.4%，反而优于 90/95 的 +134.4%/DD22.7%——
> 这是路径依赖，不是"仓位越低越赚"的规律；档位之间（70/80 是 +126.2%/DD19.8%）差距有限，
> 想更保守就往下调，想要近端行情弹性可以调回 90/95，`data/decision_study.py` 三条命令就能复核。

**验收**：`tests/test_fix4_ops.py::PositionCapTest` 三个用例覆盖
"留 200 → 上限 80%"、"不留 → 可超 80%"、"本金变大时同一笔储备不再压死仓位"。

### 21.5 配额口径更正：**只有智兔是 200/日，其余通道不限量**

**用户的更正**：智兔（zhitu）API 的每日上限是 200 次；**其他数据源只要不出故障都是不限量的**。

**改前的问题**：界面把 `akshare / 东财 / 新浪 / 腾讯 / 同花顺` 的调用**也算进了同一个
"今日已用 N / 200"的分子**，于是：
一个完全不碰智兔的账号，额度条也会一路走满、显示"额度耗尽"，

| `remaining` / `exhausted` | **专指智兔**（保留旧字段名以免破坏调用方，语义已收窄） |

界面上额度条现在显示形如 `智兔 4 次 /200 剩 196 ｜ 其它通道 598 次（不限）`。

**验收**：`tests/test_fix4_ops.py::QuotaSemanticsTest` 四个用例：
"只有智兔会耗尽"、"其它通道不消耗智兔额度"、"不限量通道被正确标注"、

## 二十二、消息判断与自动化重做：AI 为主 + 上下文条件化 + 人工 ≤50 次（2026-09-16）

这一轮不是加功能，而是**推翻了两个做错的设计**。用户的质疑都成立，逐条记录根因与改法。

### 22.1 被推翻的设计①：把"方向"当成词的性质

**用户原话**：

> 「同一个东西，自动驾驶这些，利空利多不是每天都在变得吗？怎么能这样单一地总结呢？」

**旧设计错在哪**：`learn_all()` 统计"某词出现在多少条利多消息里"，然后
`learn_all()` → `lexicon.score_text(txt, extra={词: (+1, 权重)})`——
**只要字面出现就按这个固定方向加分**。于是学出了这样的东西：

```
规划利多 34次  美元利多 32次  证券利多 17次  人工智能利多 14次
交易所利多 10次  成交额利多 3次  分化利多 3次  …
```

三类错误一网打尽：

| 错误 | 例子 | 为什么错 |
|---|---|---|
| **同词不同语境方向相反** | 「自动驾驶**事故/召回**」vs「自动驾驶**法规落地/量产**」 | 词表只看"出现了哪些词"，看不出事件被**结果动词**翻成了什么方向 |
| **把写作措辞当方向信号** | 「**交易所**利多 10 次」「**成交额**利多 3 次」 | 交易所/公告/披露/申报只是新闻**写作习惯**（"上交所公告：…"），出现频率高 ≠ 有方向信息。旧实现把"高频"误读成"有意义" |
| **方向不随行情变** | 同一条"降准"在"当日已大涨"（利好出尽）与"连续下跌"（政策托底）下方向不同 | 词表是静态的，永远给出同一个方向 |

**新设计：四路证据，任何一路都不能单独定方向**（`fundai/context.py`）：

| 路由 | 作用 | 实现要点 |
|---|---|---|
| ① **事件结果路由**（最强） | 由"**结果动词 × 宾语**"定方向 | `RESULT_BULL/RESULT_BEAR`（预增/签约/中标/投产 vs 预减/解除/终止/立案/减持）；命中即用事件方向，词表极性作废 |
| ② **否定与转折路由** | 反转与加权 | 「未/不再/未触及」→ 方向反转（系数 0.65）；「但/然而/不过」之后的分句 ×1.5（中文财经快讯里转折后半句才是真结论） |
| ③ **对象路由** | 判断作用于**谁** | market（大盘级，权重 1.0）/ sector（板块级 0.75）/ stock（个股级 **0.25**）——单只个股的减持**不该**被读成大盘利空 |
| ④ **统计反应路由**（最诚实） | 用**市场实际反应**代替词表极性 | 见 22.2 |

**措辞词黑名单**（`context.NOISE_TERMS`，27 个）：交易所/公告/披露/申报/成交额/分化/
流动性/溢价率/募集/定增/跨界/盘中/收盘… 这些词**只作说明，不产生方向**。

**验收**（`tests/test_context_interventions.py` 的 12 个用例）：

```
[OK] 同一词·事故语境   「某车企自动驾驶系统发生严重事故，宣布召回 3 万辆，股价大跌」→ bear
[OK] 同一词·落地语境   「自动驾驶法规正式落地，多家车企获批量产，产业链订单大幅增长」→ bull
[OK] 合同解除/签约     解除 4.03 亿元合同 → bear ；签约 4.03 亿元订单 → bull
[OK] 否定反转          「未能按期签约」→ bear（证据标 !签约）
[OK] 转折后半句        「营收增长但净利润预减 40%」→ bear
[OK] 措辞词不算方向      「上交所公告：新增 3 家披露申报材料」→ neutral（把握度 0.10）
[OK] 个股事件折价        「某股份公司股东减持 2%」→ neutral（个股级，不改大盘）
```
15/15 全部符合预期。

### 22.2 被推翻的设计②：用词频"学习"，而不是用市场反应"学习"

**新口径**：学习的事实来源只有一个——**含某术语的消息，次日沪深300实际怎么走**。

* `term_stats`（逐日样本，主键 `date+word`）：sign、次日涨跌、是否上涨、当日市场状态、判断来源；
* `term_agg`（条件统计）：**样本数 n**、次日上涨比例 hit、平均涨跌 chg、相对基准的 lift、
  以及 `by_regime`（按上涨/下跌/震荡分段）——**这就是"每天都在变"被显式建模的地方**；
* **样本不足不给方向**：`MIN_SAMPLES=5`（可配 `strategy.context_min_samples`），
  且打分时按 `n/(n+10)` 收缩置信度。宁缺勿滥；
* `lexicon_rows()` **不再返回 `bull/bear`**（恒为 0），只返回市场反应；界面展示改为
  「次日涨 61%+1.2% · 42样本」，不再是「利多 34 次」；
* `learned_extra()` 保留但**恒返回 `{}`**（向后兼容），方向不再由词提供。

> 一句话概括这次纠正：**词典不是"从新闻里猜词的方向"，而是"用市场的真实反应，
> 学某个术语出现的条件概率"。方向由上下文与 AI 判断，学习只提供先验。**

### 22.3 AI 为主：让 AI 的判断真正进入评分

**改前的问题**（两个，都让 AI 形同虚设）：

1. `label_items()` 只处理 `event_type == "dict"` 的"词典兜底桶"——事件规则命中过的消息
   **根本不送 AI**；
2. `news_llm_contribute` 默认 **False**：AI 判了方向也**不计入净情绪**，只做"判中性就否决"
   的降噪。等于花了 token 却不影响结论。

**改后**：

| 项 | 改前 | 改后 |
|---|---|---|
| 覆盖面 | 只送"词典兜底桶" | **整条流**，按 `🔴重要 → |本地强度| → 主题命中数` 排序取 `news_llm_cap`（默认 300）条；未覆盖的走本地上下文兜底 |
| 是否计分 | `contribute=False`（不计分） | **`contribute=True`（AI 方向直接计入消息分）** |
| 市场状态 | 不给 | **prompt 里带当日涨跌/均线/波动/情绪分位**，并明确要求"当日已大涨而消息偏多要警惕利好出尽" |
| 缓存 | 按 id 永久复用 | **按 (提示词版本, 市场状态) 分组**：`PROMPT_VERSION=3` + `context_key()`，行情阶段变了会**重判**而不是复用旧结论 |
| 失败回退 | 回退词典标签 | 回退**本地上下文判断**（结果动词/对象层级/否定转折/术语反应） |

### 22.4 人工介入：从"每个模块各说一句话"到"全系统一个额度"

**用户原话**：

> 「尽可能让 AI 进行判断，要我人工介入的每天不超过五十次！**是一共五十次！**」

**旧设计的两个毛病**：

1. 额度只写在**消息打标的文案**里（"最多 50 条复核打标"），而打标之外还有
   合并搜索回填、成交回填、重建备选池、参数改动……**全都没有计数**，用户实际点多少次无从得知；
2. 判据是"`auto_label == neutral` 的进人工额度"——**中性 ≠ AI 没把握**。
   很多中性是 AI 很确定地判成中性（例行披露），推给人工纯属浪费额度。

**改后**：`fundai/interventions.py` 统一计量（`interventions` 表，按天按类型）：

* `human(kind)` **占**预算，`auto(kind)` **不占**但留痕（可量化"AI 替你做了多少"）；
* 主界面新增**「今日人工介入额度」卡片**：`已用/50 · 剩余 · AI 自动完成 N 次 · 分类型明细`；
* 人工队列判据改为**把握度**：`review_split(items, cap, low_conf)` 只把
  `confidence < strategy.news_low_conf_threshold`（默认 0.45）的消息排进人工，
  **并按把握度升序**（先看最不确定的）；
* **把"等人点一下"的动作全部自动化**：
  - 「合并搜索回填结果」→ 每次研判前 `auto_merge_search_results()` 自动完成（有结果却合并不了才回来找人）；
  - T+1 成交确认 → 已有 `_auto_confirm()`，本轮补上**留痕**（记 `auto('order')`）；
  - 备选池过期重建 → 已有自动逻辑，同样纳入计量。

**验收**：`InterventionBudgetTest` 7 项——auto 不占额度、human 占且能发现超额、
低把握度队列只列该列的、历史可查。

### 22.5 修掉"降级提示永挂着"

**用户原话**：

> 「⚠️ 数据源降级提示 近期有失败，这个就没成功过！」

**实测到的三个叠加根因**（每一个都足以让它永久挂着）：

| # | 根因 | 证据 | 改法 |
|---|---|---|---|
| ① | **"最后一次是失败"对安静源永真**：eastmoney 当天只被调用 1 次（11:35 失败），之后净值走缓存不再调它 → 该条件永远成立 | `stale_sources=['eastmoney']` 一直不消 | 改为三条件同时成立：失败在 `STALE_FAIL_TTL`(30min) 内 **且** 连续失败 ≥`STALE_MIN_FAILS`(3) 次 |
| ② | **空判降级**：界面写「基金净值 已降级：当前由 eastmoney 供货，非首选 akshare」，而 **akshare 当天调用数 = 0** —— 它从没被真正试过 | `akshare calls=0 fail=0` | 只有"首选源确实失败过"（有失败计数**或**有故障切换记录）才判降级；否则写明"非故障降级" |
| ③ | **陈旧降级一直告警**：早上 11:35 跌到备用源、之后几十次调用全成功，`active` 仍停在备用源 → 提示挂到收盘 | `degraded_age` 数小时 | 降级事实照实记录（可排查），但**告警**要求降级发生在 `RECENT_FAIL_WINDOW`(1h) 内 |

**并且补上"能自证恢复"的机制**——这是根治的关键：

* `api_usage.probe_source()/probe_sources()`：**真实探活**新浪/腾讯/东财，结果**成败都记账**

## 二十三、三个"功能看着有、实际是死的"缺陷（2026-09-16 第二轮）

这一轮三个问题都属于同一类：**代码写了、测试绿了、功能却没生效**。逐个交代为什么测试没能拦住。

### 23.1 `STATE is not defined` —— 一行笔误打断整个消息页

**现象**：打开"消息与进化"页 → `消息数据加载失败：STATE is not defined`。

**根因**：`app.js` 的全局状态变量叫 `ST`（`let ST = null;` 存 `/api/state`），
而我在新加的 `renderBudget()` 里写成了 `STATE`：

```js
const iv = (STATE && STATE.interventions) || null;   // ← ReferenceError
```

JS 的 `ReferenceError` 会把**整个 `renderNews()` 调用链**打断，
所以表现成"消息页数据加载失败"，而不是"额度卡显示不出来"——错误位置和现象看起来毫不相关。

**为什么测试没拦住**（关键）：

| 已有检查 | 为什么无效 |
|---|---|
| `node --check` 语法检查 | `STATE` 在语法上**完全合法**，只是运行时不存在 → 查不出 |
| 后端接口测试 | 接口全部 200，后端毫无异常 |
| "元素 id 两边都在"检查 | 只验证了 html 有 id、js 有函数名，**没有检查 js 引用了 html 里不存在的元素**，也没检查全局变量是否声明过 |

**修法（两层）**：

1. 改回 `ST`，并把这段教训写进代码注释（避免下次又踩）；
2. `tests/test_frontend_static.py` 新增两个**双向一致性**检查：
   * `test_every_referenced_element_id_exists_in_html`：把 app.js 里所有
     `$("someId")` 的 id 抽出来，逐个在 index.html 里验证存在 —— 这直接命中
     "元素从未写进 HTML、`if (!el) return` 静默失效"这一类故障；
   * `test_no_undefined_globals_in_app_js`：把 `let/var/const` 声明的**大写全局变量**
     建成集合，再把 app.js 里引用的其他大写标识符（**先去注释与字符串字面量**）
     比对，任何未声明的都报出来 —— 这直接命中 `STATE` vs `ST` 这类笔误。

> 这两个测试都做过**反向验证**：故意把 `ST` 改回 `STATE`，测试立刻失败；改回来又通过。
> 一个不会失败的测试等于没有测试。

### 23.2 午间诊断"还是没有自动运行" —— 一次瞬断就放弃一整天

**现象**：计划任务 11:35 确实被触发了，但当天没有任何午间诊断。

**证据**（`data/intraday.log`）：

```
================ 2026/09/16 周三 11:35:00.58 午间复盘 ================
午间复盘跳过：实时行情不可用（网络/接口），午间诊断跳过
退出码 1
```

**根因**：`intraday._quote()` **只调一次** `indices_quote()`。而
`indices_quote()` 内部虽然已有三通道降级（新浪→腾讯→东财），
但三家**同时瞬时超时**时它返回空 → `_quote()` 直接把 `main` 置空 →
`run_midday()` 返回一句"跳过"就结束，**当天再没有任何重试机会**。

实测同一台机器晚一点手动跑就完全正常（`沪深300 上午 +0.36%`），
说明这是**瞬时网络抖动**，不是配置问题。旧实现把它当成了"今天不行就算了"。

**修法（三层，缺一层都不够）**：

| 层 | 改动 |
|---|---|
| **取数重试** | `_quote()` 重试 `MIDDAY_QUOTE_ATTEMPTS=3` 次（间隔 2.5s），返回 `quote_source` 标明是首次成功还是重试成功 |
| **跨接口兜底** | 三次都失败 → 用 `index_intraday()` 的**当日分时线**取最后一点当"上午收盘价"、按 `pre_close` 算涨跌幅。分时线与实时行情走**不同接口**，故障域不同 |
| **计划任务补跑** | `install_tasks.bat` 从 7 个任务扩到 **9 个**：新增 11:40 `fundai_intraday_retry1` 与 11:45 `fundai_intraday_retry2`；`intraday-pulse` 改为**幂等**（当日已诊断则立刻退出、不重复取数），所以补跑班次在正常情况下几乎零成本 |

**失败不再静默**：取数彻底失败时写 `data/intraday_last_error.json`，
`status()` 透出 `last_error` 字段 → 界面能明确区分"**没跑**"和"**跑了但失败**"
（否则用户只能看到"今日还没有午间复盘"，无从判断）。

### 23.3 午间诊断结果"要放显眼位置" —— 结果它压根没显示

## 二十四、估值缩水假回撤 + 行情播报刷屏（2026-09-16 第三轮）

### 24.1 "1000 的资金哪里回撤 58 了？"

**用户原话**：

> 「风险过滤信号虽未触发极端预警，但账户自峰值回撤已达58.2%，触发硬性风控机制，
>   强制要求权益仓位降至25%并进入5日防御冷却期。统计数据模块是不是有问题？
>   1000的资金哪里回撤58了？！」

**用户是对的**。真实数字与那次研判的数字对比：

| 项 | 那次研判（错） | 实际情况 |
|---|---|---|
| 总资产 | **421.00** | **992.21** |
| 峰值 | 1007.42 | 1007.42 |
| 回撤 | **58.2%** | **1.51%** |

`421.00 = 现金 121.01 + 债基 299.99` —— **正好少了全部股基 571.21**。
研判原文里那句「**当前股基市值为0**」就是铁证。

**根因链条（三层，逐层都要堵）**：

| # | 层 | 问题 |
|---|---|---|
| ① | `nav_latest_map` | 取价失败 → 该持仓**整条不进 dict**。两条路径都会触发：在线通道全失败；或 `fund_latest→fund_history(need_from=近45天)` 的 `_serve()` **按日期窗口过滤缓存**后返回空 |
| ② | `_valuation` | `if not pair: continue` —— 把"**没取到价**"和"**价值为 0**"混为一谈，total 静默缩水 |
| ③ | `strategy.plan` | 拿这个被低估的 total 去算回撤 → 15% 阈值一撞就过 → 强制 25% 仓位 + 5 天冷却 |

**讽刺的是这个 BUG 有前科**：`nav_latest_map` 的 docstring 里就写着 2026-09-11
"实测 1007.42 → 420.95，看起来像亏光了，其实只是没取价"。当时只修了
"没遍历持仓"那一条路径，**剩下两条漏价路径原样存活**，三个数字一模一样地复现了。

**修法（三层对应）**：

1. **`last_known_nav(code)`**：直接读缓存里**最后一条已知净值**，**不做任何日期过滤**。
   取价失败时逐只回退到它 —— 宁可估值略旧，绝不缩水。（两条失败路径都补齐了）
2. **`_valuation` 如实报缺**：返回 `complete` / `missing`，不再假装"有持仓就一定有价"。
3. **风控闸门**：`ctx["valuation_complete"]=False` 时，
   **回撤/本金亏损两条硬风控一律不触发**，并在研报文里说明
   「【估值不完整】有 N 只持仓没取到净值（…），本次不做回撤判定，也不据此降仓」。
   宁可不防守，也不能凭错数乱砍仓位。

**验收**：`tests/test_valuation_integrity.py` 4 项，其中最关键的一项同时断言两面——
不完整时**不**触发回撤风控，完整时**仍**触发（证明闸门看的是"完整性"而不是"数字大小"）。

**误判的善后**：那次错误把 `risk_armed` 置 0 并写了 `risk_lock_until=2026-09-23`。
这些是假信号的产物，已清除并重新武装，然后重跑了当日研判。
重跑结果：观点 `缩量反抽，趋势承压`（-15），**无任何回撤风控**，估值完整（5/5 有价），
真实回撤 **1.51%**。

### 24.2 "消息界面重复的消息还是太多了" —— 那些不是新闻，是行情播报

**用户原话**：

> 「比如那种财联社报黄金啥的涨跌之类的，还有类似这种的深证成指涨1.01%，现报13422.186点；
>   上证指数涨0.30%，现报3875.776点；创业板指涨1.82%，现报3307.017点。，
>   全部都让AI默认读取就行了，只是单纯的消息面，根本不构成利空利好」

**用户判断得对，而且这是"去重"解决不了的问题**：

* 这类内容不是新闻而是**报价**。市场已实时定价，对"次日方向"不含任何增量信息
  —— 判它利好/利空本身就是错的（会污染净情绪）；
* 标题里的**数字每次都在变**（`涨1.01%` → `涨0.98%`）→ 标题归一化去重**必然失效**；
* 旧逻辑的 `collapse_same_template` 只能把它们标成"重复"**但照样显示**，用户看到的仍是满屏重复。

**修法：识别为一类 → 整类归档**（`screening.detect_broadcast`）：

| 判据 | 说明 |
|---|---|
| 命中**行情标的** | 指数（含境外：泰国综合指数/韩国综合指数…）、商品（黄金/原油/铜…）、汇率（离岸人民币…）、国债期货 |
| 命中**报价动作** | 现报/报/涨跌/突破/站上/触及/失守/跌破 |
| 且带**百分比或点数** | 区分于"成交额 1.2 万亿"这类无方向描述 |
| **不含真事件词** | 政策/发布/签约/业绩/减持/立案… 一律保留 |
| **不含板块/个股词** | 「黄**金股**集体涨停」是板块事件，不是商品报价 → 保留 |
| **不是人写的复盘** | 早盘/午评/收盘/涨停分析/一图看懂/连板 → 保留 |
| **不是历史性表述** | 历史/首次/新高/新低/创纪录 → 保留 |

配套：

* 入库时自动打 `market_broadcast` + `auto_label=irrelevant` + `decided_by=auto_archive`
  → 不占 AI 判断预算、不进净情绪、不进人工队列；
* `broadcast_key()` 把数字全部替换成 `#` 再分组，**彻底解决"数字变化导致去重失效"**：
  `深证成指涨1.01%，现报13422.186点` 与 `…涨0.98%，现报13380.500点` 归为同组；
* 每组只留**一条代表条**（标题带"当日 N 条同类，已自动归档"），其余原文存入
  `archived_items` 表 —— 归档但**可追溯**，不是丢掉；
* 前端新增 `📦AI归档` 里的 `broadcast` 分类，并显示当日播报条数；
* CLI：`python app.py archive-broadcasts [--dry-run]`（幂等，可反复运行清理存量）。

**验收**：`tests/test_broadcast_filter.py` 5 项 / 18 个例子。
其中**"绝不能误归档真消息"与"必须归档播报"同等重要** ——
归档掉"央行降准"或"黄金股涨停"就是把真信号丢了。实测 18/18 全对。

实测效果：全库 26 条播报已归档；今日 194 条里只剩 2 条代表条（归入 AI 归档）。

> **一个诚实的说明**：我先量了"到底还剩多少重复"——全库 1373 条里，
> 标题**完全重复的 0 组**、去掉日期前缀后仅 **5 组 10 条**。
> 也就是说用户看到的"重复"主要就是那 26 条行情播报刷屏，而不是真的重复入库。
> 所以这次修的是"把播报从消息流里摘出去"，而不是去把去重算法调得更激进。

## 二十五、量化决策与综合最优组合（2026-10）

这一节记录本轮对**选基资金分配**与**基金级风控**的改造。结论全部来自真实基金级
引擎（`Engine.backtest`，point-in-time 逐日重建池、真实申赎费、T+1/最短持有），

### 25.1 改了什么

1. **组合构建层**（新模块 `fundai/portfolio.py`）
   - `equal` 等权、`inv_vol` 逆波动、`min_var` 收缩协方差最小方差、
     `adaptive` 制度自适应；
   - 统一约束：权重和为 1、单基金上限 `max_fund_weight=0.45`、
     同主题合计上限 `max_theme_weight=0.70`、起购额、整数元、末位吃余数；
     数据不足自动回退等权，组合异常回退旧口径；
   - 决策文案输出「综合最优组合：权重 + 事前年化波动 + HHI」。

2. **制度自适应（默认）**
   - 趋势上行：沪深300 20 日动量 > 0 **且** 市场评分 ≥ 25 → 用旧动量加权
     （集中强势主题）；
   - 其余状态 → 等权分散；
   - 趋势信号可选 `ma_align` / `mom20` / `either`，默认 `mom20`（比 MA20>MA60>MA200
     的确认更快，急跌后反弹不至于完全错过）。

3. **基金级止损/止盈改为开关，默认关闭**
   - `risk.fund_stop_loss_enable`、`risk.fund_take_profit_enable` 两个独立开关；
   - 关闭后**指数级**风控仍然生效：跌破 MA60/MA120 各减 0.10、峰值回撤 10%
     冷却 5 天、组合止损 −15%、权益硬上限 80%；
   - 想恢复旧行为：`portfolio_method="legacy"` + 两个开关打开即可。

4. **回放/线上一口径修复**
   - `Engine.simulate` 现在注入 `ma_align` / `vol_rank`，与 `run_daily` 同口径；
     此前回放里 adaptive 与调整带永远看不到制度状态（回放会退化成等权）；
   - `_fund_factors` 与回放 factors 增加 60 日收益序列，供 `min_var` 估计协方差；
   - 研究层 `data/harness.py` 的缓存签名改为**真实缓存键**（`kline_000300_SH.json`
     与东财兜底键），避免 `harness_base.json` 永不失效、窗口停在旧日期。

### 25.2 五窗口对照（真实基金级引擎，数据边界 2017-09-28 → 2026-11-05，收益%/最大回撤%）

统一口径：`equity_base_fixed=0.80`、`equity_hard_cap=0.80`、`liquidity_reserve_yuan=200`，
每个变体只改一件事；结果由 `python data/decision_study.py --jobs 1` 生成
（`data/decision_study.json`，含逐日序列与年度分解）。

| 变体 | 全历史 | 牛市 | 熊市 | 震荡 | 近12个月 |
|---|---:|---:|---:|---:|---:|
| **live：adaptive/mom20 + 关基金级风控** | **+187.0 / 21.4** | +16.4 / 11.9 | **−12.7 / 14.1** | **−7.6 / 10.6** | −1.9 / 22.7 |
| legacy_live：旧动量加权 + 基金级止损/止盈 | +75.7 / 24.1 | **+25.5 / 11.3** | −14.7 / 14.7 | −8.2 / 12.9 | **+6.9 / 20.6** |
| adaptive/ma_align | +162.7 / 21.4 | +13.0 / 12.4 | −11.7 / 13.7 | −7.9 / 10.8 | +2.1 / 22.6 |
| 等权（不切换） | +138.9 / 21.4 | +12.9 / 12.4 | −11.7 / 13.7 | −7.9 / 10.8 | +2.2 / 22.6 |
| 逆波动 | +156.0 / 22.7 | +7.3 / 15.3 | −19.7 / 19.7 | −7.9 / 10.8 | −0.2 / 22.6 |
| 最小方差（收缩协方差） | +154.9 / 21.8 | +12.3 / 12.8 | −14.3 / 14.3 | −8.0 / 10.6 | −0.5 / 23.2 |

| 纯 20 日动量因子（不改风控） | +151.5 / **25.1** | +6.1 / 15.8 | −14.9 / 14.9 | −7.5 / 10.8 | +4.0 / 24.4 |

读法（重要）：
- 新默认在**全历史、熊市、震荡**三段更好，回撤 21.4% 也优于旧策略 24.1%；
- 新默认在**牛市窗口**明显弱于旧 live（+16.4% vs +25.5%）：`mom20` 在急跌后的
  反弹初期仍会滞后，非上行状态用等权会稀释最强主题。这是有意的取舍，
  不是疏漏——只看牛市窗口会得出相反结论；
- **近 12 个月旧 live 更好**（+6.9% vs −1.9%）。该窗口跨度短、单一市场状态，
  且所有变体都只在 −2%~+7% 之间，属于噪声级别；不能拿它当选型依据，
  但必须知道：**如果未来继续走成近 12 个月这种形态，新默认会落后**；
- 等权单用 +138.9% < adaptive +187.0%，说明增益来自“何时集中、何时分散”
  的制度切换，而不是“等权”本身；
- 只改风控不改分配（旧动量加权 + 关基金级风控）只有 +126.2%，且近 12 个月
  回撤 25.8% 越界；两个改动必须一起用才是 +187.0%；
- 逆波动（牛市 +7.3%、熊市 −19.7%）与最小方差（+154.9%，牛市 +12.3%）
  都不如 adaptive，因此只作为可选项保留，**不是默认**；
- 把因子换成纯 20 日动量，全历史 +151.5% 但回撤 25.1% 越约束、牛市段只有
  +6.1%——**现有因子权重（mom 0.65 / mom5 0.15 / vol 0.20 / theme_heat 0.10）
  保持不变**，本轮没有证据支持改动它。

### 25.2b 仓位档位复核（同一份最新数据，adaptive/mom20 + 关基金级风控）

| 档位 | 全历史 | 最大回撤 | 近12个月 | 结论 |
|---|---:|---:|---:|---|
| **基准 80% / 上限 80%（最终默认）** | **+187.0%** | **21.4%** | −1.9% | 全历史最高、回撤最低 |
| 基准 90% / 上限 95% | +134.4% | 22.7% | +12.4% | 收益更低；近12月更高 |
| 基准 70% / 上限 80% | +126.2% | 19.8% | +6.1% | 最保守档 |
| 旧策略 90% / 95%（legacy + 基金级风控） | +98.1% | 23.7% | +10.2% | 对照 |

> 80/80 比 90/95 收益更高、回撤更低，**不是“仓位越低越好”**，而是同一条路径上
> 触发风控与再平衡的时点不同（路径依赖）。三档差距在 20%~50% 之间摆动，
> 说明单路径回测的分辨率有限；选 80/80 是因为它在“全历史收益优先 + 回撤≤25%”
> 这个口径下最优，且与旧策略的差距（+187% vs +98%）远大于档位之间的差距。
> 想要更保守可切 70/80；追求近端行情弹性可切 90/95，但要接受全历史更低。

### 25.2c 为什么必须重跑（一次缓存失效事故）

本轮最初的研究结果全部偏低且不一致，根因是 `data/harness.py` 的缓存签名盯的是
`kline_000300.SH.json`，而落盘名经消毒后是 `kline_000300_SH.json` —— 签名恒为 `na`，
`harness_base.json` 永不失效，研究窗口停在旧日期，而网页/CLI 回测用的是最新行情，
于是出现“90% 档 DD 30.4%”这种**在正确数据上不成立**的数字（正确值是 22.7%）。
修好签名后所有表格重算，本节数字才是可复现的口径。这也解释了 README §20
“常驻服务跑旧代码”之外的第二种“跑得出数字但数字是旧的”失效模式。

### 25.3 时间顺序留出段（当前数据，切分日 2023-09-04）

| 策略 | 训练段 2017-09→2023-09 | 留出段 2023-09→2026-11 | 留出段回撤 |
|---|---:|---:|---:|
| 旧策略（legacy + 基金级止损/止盈） | +19.8% | +46.7% | 17.4% |
| **新默认（adaptive/mom20 + 关基金级风控）** | **+57.7%** | **+82.0%** | **17.1%** |

留出段是**样本外**（参数与规则全部在 2023-09 之前的数据上定稿，之后没有再调过），
新默认训练段与留出段都更好。这是本轮最有力的一条证据：+187% 不是把参数
拟合到全样本的结果。仍需注意它只是**一次**切分，不是滚动 walk-forward。

### 25.6 已知边界（必须一起读）

1. **单路径方差大**：同一套逻辑只改基准仓位，全历史收益是 90/95 档 +134.4%、
   80/80 档 +187.0%、70/80 档 +126.2%（非单调）。这不是“越低越赚”的规律，
   而是风控触发与再平衡时点不同导致的路径依赖；只能看平台与多窗口，
   不能追单点最优。
2. **牛市捕获下降**：新默认在 2020-03→2021-01 的急反弹窗口 +16.4%，
   旧策略 +25.5%。如果目标是“牛市弹性优先”，可把 `adaptive_signal="ma_align"`
   或把 `adaptive_bull_score` 调低（更常集中），但要用 `decision_study.py` 复核。
3. **近 12 个月跑输**：新默认 −1.9%，旧策略 +6.9%。这段行情短且所有变体都接近，
   但**这是真实的方向性差异**：如果你的使用期就是未来几个月，不能假设新默认更好。
4. **样本外只做了一次时间切分**（2023-09-04），不是滚动 walk-forward；结论仍需
   随新数据滚动复核。
5. **数据边界**：本节全部数字为 2017-09-28 → **2026-11-05**（修复研究缓存签名后
   重算）；`data/decision_study.py` 每次重跑会随数据延伸变化，见 25.2c。
6. **不构成投资建议**：所有收益都是历史回放，不是未来承诺。
